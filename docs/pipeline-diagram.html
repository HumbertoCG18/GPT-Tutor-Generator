1 · Fluxo completo (depois — v4)

entrada

📄 SYLLABUS.md → linhas candidatas

_parse_syllabus_timeline → _build_timeline_candidate_rows

  • Parseia tabela de cronograma do syllabus (data + conteúdo por linha).
  • Cada linha vira {index, date_dt, date_text, content}.
  • Gatilho: só roda se há syllabus; senão usa .timeline_index.json em disco (preserva atribuições).
agrupamento

🧩 Linhas → blocos temáticos

_rows_belong_to_same_thematic_block

  • Acumula linhas consecutivas no mesmo bloco enquanto forem do mesmo tema.
  • Quebra o bloco se a linha é revisão/prova (_timeline_row_is_review_or_assessment).
  • Linha de continuação junta se compartilha tokens e não é só âncora de unidade.
  • Senão: junta se core text é substring OU overlap de tokens ≥ 2.
  • id = bloco-NN (ordem cronológica, determinístico).
período

🗓 period_label + sessions

_timeline_period_label · _extract_block_sessions

  • Prefixo de duração resolve ambiguidade de data: "5 dias · 11/03 a 25/03".
  • sessions[] = ocorrências individuais (1 por data), com card_evidence anexado.
tópico — matcher

🎯 Atribuição de tópico (taxonomy)

_assign_timeline_block_to_topic → _score_timeline_block_against_taxonomy_topic

  • Score do bloco contra cada tópico da taxonomy via sinais (topic_text, conteúdo das linhas).
  • Subtópico ganha bônus +0.18.
  • Vencedor reprovado (weak) por faixa: min_score 1.85 / 1.75 / 1.35 e min_conf 0.8 / 0.9 / 0.72.
  • topic_candidates[] guardado com relative_confidence = score / winner_score — alimenta o voto adiante.
confidence = clamp( (winner_score − runner_up_score) + winner_score·0.20 , 0, 1 )
unidade — 3 camadas

🏷 Atribuição de unidade (cascata)

  • 1. Via tópico: se topic não-ambíguo & confidence ≥ 0.65 → _derive_unit_from_topic_match.
  • 2. Texto×unidade: _assign_timeline_block_to_unit — score do conteúdo; topic_text pesa ×0.7; exige winner ≥ 1.0 e gap ≥ 0.35.
  • 3. Voto (Fase 3): _vote_unit_from_topic_candidates — quando 1+2 falham.
  • 4. Herança: bloco "soft continuation" herda unidade do vizinho (conf ≥ 0.51).
VOTO (Fase 3): top_k=5 candidatos, descarta score < 0.10 peso = Σ score por unit_slug · vence se winner_weight / total ≥ 0.60 (dominance) confidence = clamp( winner_weight/total · 0.6 , 0.30, 0.55 )
Fase 4 — fallback

🔤 Resolução de label do tópico (camadas)

_resolve_block_topic_label → _humanize_topic_text

  • 1. manual → manual_topic_label (curation) · 2. taxonomy → primary_topic_label do matcher.
  • 3. topic_text_fallback → humaniza topic_text cru (tira stopword de borda, capitaliza, trunca 60).
  • topic_source vira badge na UI. Fallback nunca preenche slug (display-only).
Fase 1 — classifier

🏛 Classificação de kind

classify_block — fonte única, determinística, sem LLM

  • Prioridade: manual_kind_override → exceção CLASS_INTRO (plano de ensino/ementa) → KIND_KEYWORDS em ordem.
  • Ordem: holiday → suspended → makeup → academic_event → results → deliverable → workshop → office_hours → planning → reserved → assessment (regex p1-4/pf) → review.
  • Fallback: tem unit/topic → CLASS · texto com substância (≥8 chars ou ≥2 tokens) → CLASS · senão → UNKNOWN.
  • 14 kinds fechados (enum BlockKind).
Fase 5 — curation

✍ Merge de overrides manuais

_apply_curation_overrides ← apply_block_curation

  • Lê course/.timeline_curation.json (keyed por block_id) — store separado, sobrevive ao rebuild.
  • Injeta manual_kind_override / manual_topic_label e re-deriva kind + topic.
serialização

💾 _serialize_timeline_index → .timeline_index.json

  • Injeta kind = classify_block(block) no momento de gravar (sempre re-derivado).
  • version: 4 · emite manual_*/topic_source só quando presentes.
  • block_status NUNCA é gravado — derivado em read-time.

🖥 Dashboard (Tkinter) — 100% schema-driven

  • Filtros por kind (checkboxes) · dropdown de reclassificação → grava em curation → reload.
  • Zero heurística local: tudo vem do schema.

2 · Como cada cálculo decide (detalhe)

classify_block()

Entrada: topic_text, primary_topic_label, period_label, topics[], unit_slug, manual_kind_override

Normaliza (NFKD + lower + [a-z0-9 ]). Matching: frase = substring; 1 palavra = token exato (≥4 chars).

Mais específico bate primeiro → feriado/prova nunca viram "aula" por acidente. CLASS_INTRO protege o bloco de apresentação que contém a palavra "avaliação".

_score_timeline_block_against_taxonomy_topic()

Constrói sinais do bloco e pontua contra cada tópico/subtópico da taxonomy (aliases considerados internamente).

score = score_base(signals, topic) + (0.18 se kind == "subtopic")

Faixas de min_score/min_conf evitam casar tópico genérico fraco — bloco fica sem tópico em vez de receber um errado.

_assign_timeline_block_to_unit()

Entrada: conteúdo das linhas + topic_text contra unit_index.

score = txt_unit(full_text) + txt_unit(topic_text)·0.7 guarda: winner ≥ 1.0 AND |winner−runner| ≥ 0.35 conf = clamp((winner−runner) + winner·0.18, 0,1)

Gap mínimo impede atribuição quando duas unidades empatam (ambíguo).

_vote_unit_from_topic_candidates() Fase 3

Quando matcher direto falha mas há topic_candidates[] apontando consistentemente pra uma unidade.

top_k=5 · descarta score < 0.10 peso[unit] = Σ score · vence se peso/total ≥ 0.60 conf = clamp(peso/total · 0.6, 0.30, 0.55)

Confidence capada baixa (0.30–0.55): é inferência indireta, não match direto. Resolveu 27 blocos missing_unit.

_resolve_block_topic_label() Fase 4

manual_topic_label → source=manual (+slug) primary_topic_label → source=taxonomy (+slug) humanize(topic_text) → source=topic_text_fallback "" → source=""

Fallback é só apresentação: preenche label pra UI mas não inventa slug (slug = vínculo real com taxonomy). Resolveu missing_topic 24→0.

derive_block_status() Fase 1

unknown → needs_review non-academic kind → non_applicable requires(unit) & vazio → needs_unit requires(topic) & vazio → needs_topic requires(files) & 0 ses → needs_files senão → ok

KIND_REQUIREMENTS é a tabela-verdade. Puro, read-only, nunca persistido.

4 · Pontos pra você revisar / possíveis otimizações

Perguntas abertas — o fluxo faz sentido?

  1. Ordem unidade vs tópico: hoje tópico é resolvido antes da unidade, e a unidade pode vir do tópico (camada 1). Mas o voto (camada 3) também usa topic_candidates. Há acoplamento circular leve: tópico fraco → não vira unidade direta → cai no voto. Faz sentido, mas vale confirmar se a ordem está como você imaginou.
  2. Confidence do voto capada em 0.55: intencional (inferência indireta). Se downstream filtra por confidence ≥ 0.65 em algum lugar, blocos resolvidos por voto seriam descartados. Verificar consumidores de unit_confidence.
  3. Thresholds mágicos: 0.10 / 0.60 / 0.65 / 1.0 / 0.35 / 1.85·1.75·1.35 estão espalhados como literais. Otimização: centralizar num bloco de constantes nomeadas no topo (auditável, ajustável sem caçar).
  4. Fallback de tópico humanizado: pode produzir label "bonito" pra bloco que na verdade deveria casar taxonomy. O topic_source badge expõe isso na UI — mas vale um audit periódico de quantos blocos vivem em topic_text_fallback (sinal de taxonomy incompleta).
  5. Re-derivação dupla: _apply_curation_overrides re-deriva kind/topic, e _serialize re-classifica de novo. Idempotente, mas é trabalho repetido. Otimização menor: serialize poderia confiar no kind já no bloco.
  6. Voto ignora ordem temporal: herança (camada 4) usa vizinho, mas o voto não considera proximidade temporal dos candidatos. Possível melhoria: ponderar candidatos por adjacência de período.

Onde dá pra otimizar (custo/risco baixo)

  1. Extrair TimelineThresholds (dataclass de constantes) → testável e ajustável.
  2. Cache do topic_index/unit_index por curso (hoje recalcula sinais por bloco).
  3. Métrica contínua: % de blocos por topic_source e por status no audit → dashboard de saúde da taxonomy (já é quase a Fase 6/CI).
  4. UI: badge de topic_source e unit_confidence visível no header (hoje só status) pra curadoria mais informada.
