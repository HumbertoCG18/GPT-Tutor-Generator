Proposta: enum fechado BlockKind (14 valores derivados dos dados reais) + classificador único + status sempre derivado. Schema versionado (v4) + validação em CI. Pré-requisito do material-agnostic-refactor.md.

Como block_status é derivado (read-time)

Pseudo-código

def derive_status(block):
    req = KIND_REQUIREMENTS[block.kind]
    if not req:                       # holiday, suspended, ...
        return "non_applicable"
    if block.kind == "unknown":
        return "needs_review"
    if req.unit and not block.unit_slug:
        return "needs_unit"
    if req.topic and not block.primary_topic_label:
        return "needs_topic"
    if req.files and block.n_entries == 0:
        return "needs_files"
    return "ok"

Os dois bugs estruturais que o plano resolve

1. missing_unit — 27 blocos (29%)

Conteúdo real (microservicos spring, halting problem, logica predicados) sem unit. Matcher de unidade falha.

3 hipóteses a investigar na Fase 3:
  • A. Keyword index da unit só contém literal do título (não termos derivados). Fix: bootstrapping intra-curso usando topic_text de blocos já casados.
  • B. Threshold de score alto demais. Fix: baixar + fallback fuzzy.
  • C. Matcher só lê topic_text, ignora date_text. Fix: incluir ambos no input.

Meta: missing_unit ≤5% por curso.

2. missing_topic — 22 blocos (24%)

Bloco tem unit + topic_text rico mas taxonomy do curso não tem entrada que bate (dafny, isabelle, cook levin, devops).

4 camadas de fallback (Fase 4):
  • 1. Match exato no taxonomy (atual)
  • 2. Match por alias
  • 3. Fallback: topic_text normalizado vira label provisório
  • 4. Override manual via curation

Novo campo topic_source ∈ {"taxonomy","alias","fallback","manual"} driva cor do badge. Meta: missing_topic = 0%.

Pontos onde você pode redirecionar

D1 — Tamanho do enum (14 kinds é o certo?)

Opções:

  • Menor (6 kinds): class, assessment, review, non_academic, makeup, unknown. Simples, mas perde distinção entre feriado/suspensão/evento/atendimento (todos viram non_academic). UI mostra ícone genérico. menos código, menos info
  • Médio (14 kinds — proposto): Cada categoria observada vira kind. Cobertura 100% dos casos auditados. recomendado
  • Maior (20+ kinds): Sub-divide assessment (P1, P2, sub, recuperação), holiday (feriado nacional vs municipal), etc. Granularidade extra raramente útil. over-engineering
D2 — Strategy de fallback de topic (Fase 4)
  • A. Só taxonomy + alias. Blocos não cobertos ficam vazios. Aluno vê "—" no tutor. conservador
  • B. Adicionar fallback determinístico (topic_text normalizado). Sempre tem label. Risco: label cru, sem capitalização certa. recomendado
  • C. Usar Gemini/LLM pra gerar label quando taxonomy não bate. Mais bonito, mas custo escala + não-determinístico. caro
D3 — Quando re-rodar pipeline nos cursos existentes
  • A. Pós-Fase 2 (kind preenchido, sem fix de unit/topic ainda). Rápido mas dados ainda incompletos. prematuro
  • B. Pós-Fase 4 (kind + unit + topic todos OK). Re-roda uma vez, fica redondo. recomendado
  • C. Nunca — só novos cursos usam schema v4. v3 vira read-only legacy. divide ecosystem
D4 — UI: editor manual de kind?
  • A. Sem editor — classifier sempre vence. Se classifica errado, usuário ajusta keyword. puro
  • B. Dropdown de override no bloco. Salva em curation.json. Rebuild preserva. recomendado
  • C. Edição inline de keywords do classifier via UI. complexo
D5 — Ordem de execução das fases
  • A. Sequencial (0→7): Cada fase entrega valor isolado. Pode parar em qualquer ponto. recomendado
  • B. Fix-first (3→4 antes de classificar): Resolver missing_unit/topic primeiro. Mas sem kind, UI continua confusa. prematuro
  • C. UI-first (5 antes do resto): Mostrar mock com dados fake. Vê resultado antes. Mas mock pode esconder problema de dado. cosmético
D6 — Lidar com cursos que ainda não foram processados

Hoje só temos 5 cursos auditados. Outros cursos (futuros) podem ter kinds que não cobrimos.

  • A. Audit CI bloqueia: se um curso novo gerar unknown >5%, build quebra → força adicionar keyword/kind. recomendado
  • B. Permitir unknown silenciosamente. Sem ruído, mas defeitos acumulam. drift
  • C. Auto-aprender keywords novas via LLM. Complexo + não-determinístico. over-engineering

Anti-objetivos (o que NÃO faremos)

  • Não persistir block_status. Sempre derivado em read-time.
  • Não ramificar lógica de kind. Toda heurística vive em classifier.py.
  • Não quebrar leitura de v3. Backfill lazy ao abrir índice antigo.
  • Não atrasar code-summarization-gemini.md. Planos rodam em paralelo.
  • Não criar novo formato de output. .timeline_index.json continua canônico.
  • Não inferir kind via LLM. Só keywords + regex. Determinístico, barato, auditável.
