Overview do Sistema — GPT-Tutor-Generator

Visão geral viva do projeto · abas 1–5 sistema de atribuição · 6 pendências · 7 relatório de sistema · 8 concluído · mantido atualizado com a arquitetura atual

Duas fontes, um artefato. O Plano de Ensino (ementa + conteúdo programático) vira a taxonomy (unidades, subunidades, aliases). O SYLLABUS (tabela do cronograma) vira blocos (semanas agrupadas por tema). O matcher cruza os dois e grava tudo no .timeline_index.json v4, que alimenta a UI e o anexo de materiais.

fonte/artefato processo dado derivado curadoria (dado, não código)

Como o número decide. Cada bloco é pontuado contra os tópicos da taxonomy; a unidade vem em cascata de 4 camadas (primeira que passa o limiar ganha). Tudo determinístico — keywords + overlap de tokens, zero LLM.

Limiares reais: tópico weak se score < 1.85/1.75/1.35 (por faixa) ou conf < 0.8/0.9/0.72. Unidade via tópico exige conf ≥ 0.65; matcher direto exige winner ≥ 1.0 e gap ≥ 0.35; voto exige dominância ≥ 0.60. unit: tag ≥ 0.65 · subunit: ≥ 0.60 · bloco: ≥ 0.50.

Caso real — TCC, "Halting Problem". O cronograma diz Halting Problem (inglês); a ementa diz Problema da Parada (português). Zero token em comum → o matcher acha 0 candidatos. O fallback humaniza o label pra UI, mas a unidade fica vazia. A curadoria fecha (1 clique, persistido).

Mesmo padrão: Theorema de Rice (typo) e Entscheidungsproblem (granularidade da taxonomy). Todos resolvidos por manual_unit_slug → unidade-03-problemas-indecidiveis no .timeline_curation.json, que sobrevive ao rebuild.

Cadeira nova = zero refactor. O sistema se molda por dado, não por código. Solta plano + syllabus, o automático resolve ~90%, o gate sinaliza o resíduo, o professor cura os poucos blocos duros 1x na UI. Nunca se mexe no código.

Garante 100% em qualquer disciplina/idioma porque a curadoria é o último elo — auditável, determinístico, sem dependência de modelo. Adicionar cadeira nunca dispara refatoração.

Material → bloco. Cada arquivo no manifest.json recebe tags gerenciadas (unit:, subunit:, bloco:) por confiança, ou uma atribuição manual absoluta. A UI agrupa os materiais sob cada bloco do cronograma.

Critério (content_taxonomy.py): unit: conf ≥ 0.65 · subunit: ≥ 0.60 · bloco: ≥ 0.50 (e não-ambíguo). manual_timeline_block_id e manual_unit_slug têm precedência absoluta (conf = 1.0).

Pendências — sistema de atribuição. O que falta implementar (P0 já mergeado está na aba "✅ Concluído"). Detalhe no plano-mestre, specs/planos e no handoff docs/reports/2026-06-17-handoff-atribuicao.md (estado: P1 fechado exceto o fallback adiado pro P2; P3.4 feito). Contexto institucional em .mex/context/institutional.md.

O risco: mexer no INPUT de uma camada de cima muda o resultado silenciosamente. Possivelmente exige refatorar/remover/fundir camadas redundantes (ligado ao P2 resolver-único e à limpeza pós-cutover).

  • UNIDADE manual_unit_slug (1.0) → auto scorer (auto_map_entry_unit_fn + boosts do tag_profile) → reconcile_unit_with_block (file_map.py:598): bloco define unidade se block_confidence ≥ unit_confidence, senão mantém + flag conflito.
  • SUBUNIDADE manual_subunit_slug (1.0) → auto subtopic scorer, gated SUBUNIT_TAG; input enriquecido com resumo Gemini de código (code_curation, content_taxonomy.py:1070) — consumidor de produção à parte (mais um sistema).

Não são "aditivos". Por isso o S0 ficou estritamente inerte e esses dois saíram para o S0b (eval-gated, dry-run+rebuild_diff+gold, gated por timeline fresco).

Esta pendência consolida o MAPA que orienta essas remoções — nada deletar sem entender quem sobrepõe quem.
